# 项目现状说明

本文档基于 `2026-05-21` 当前工作区代码、配置文件、测试用例和一次本地命令验证整理而成。

重要说明：

- 当前仓库工作区不是干净发布态，存在一批未提交改动，因此本文描述的是“当前开发态现状”，不等同于某个稳定 release。
- 本文重点回答“这个项目现在已经做到哪里、主要怎么实现、当前还缺什么”，不替代 PRD 和代码契约。

## 1. 项目定位

这是一个基于 `React + Django + LangGraph` 的 AI 对话应用，当前已经不是纯静态界面，而是具备以下完整链路的可运行项目：

- 用户注册、登录、退出、个人设置
- 会话创建、历史会话列表、消息持久化
- 文档上传（当前只支持 `.docx` 和 `.pdf`）
- 基于当前会话附件的 RAG 检索
- 普通同步回复和流式回复两条消息发送链路
- 管理员登录与用户管理页面

从代码完成度看，这个项目已经超过“前端 Demo”阶段，处于一个可本地运行、可测试、可继续迭代的 MVP/早期产品态。

## 3. 当前目录职责

- `frontend/`：React 前端，包含页面、聊天组件、认证上下文和 API 封装。
- `backend/apps/accounts/`：注册、登录、登出、个人设置、改密、管理员用户管理。
- `backend/apps/chat/`：会话、消息、附件、AgentRun、知识索引记录。
- `backend/ai/`：LangGraph 编排、模型调用、文档读取、切片、embedding、检索、工具绑定。
- `docs/`：PRD、契约文档、架构说明和维护文档。
- `.memories/`：项目记忆文档，当前已沉淀前端聊天相关模块说明。

## 4. 已实现的主要能力

### 4.1 用户与权限

- 已实现注册、登录、退出、`/api/auth/me/` 当前用户接口。
- 登录态通过 `HttpOnly Cookie` 承载 token。
- 对 Cookie 鉴权的非只读请求启用了 `CSRF` 校验。
- 普通用户无法访问管理员接口。
- 普通 `staff` 不能提升、降级、删除或修改特权账号的角色字段，`superuser` 才能修改管理员角色。

### 4.2 对话能力

- 支持创建会话、读取会话列表、读取消息列表、修改会话标题、删除会话。
- 当前会话列表接口只返回当前用户最近 `20` 条会话。
- 删除会话已经是“硬删除”语义，不再只是逻辑删除。
- 发送消息时，会持久化：
  - 用户消息
  - AI 消息
  - `AgentRun` 运行记录

### 4.3 文件上传与知识检索

- 支持上传 `.docx` / `.pdf`。
- 上传时会做服务端验证，不只相信扩展名和浏览器上报的 `content_type`。
- 上传成功后会创建 `Attachment`，并同步创建 `KnowledgeDocument` 索引记录。
- 当前上传接口本身不阻塞做完整索引，文档初始状态通常是 `pending`。
- 当前会话首次检索时会按需补索引历史附件。
- RAG 检索范围限定在“当前用户 + 当前会话”。
- assistant 消息会保存 `sources`、`used_chunks`、`is_rag_answer`，历史消息刷新后仍可展示来源信息。

### 4.4 AI 调用

- 普通回复链路：`POST /api/chat/send/`
- 流式回复链路：`POST /api/chat/send-stream/`
- 流式接口使用 `NDJSON` 增量返回 `start / delta / done` 事件。
- LangGraph 已接入工具调用，工具能力包括：
  - 读取当前用户最近会话
  - 读取当前会话最近消息
  - 读取用户设置
  - 检索当前会话知识片段
  - 读取某个附件相关片段
  - 读取当前会话最近上传文档全文
  - 按附件 ID 读取文档全文
- Agent 工具是后端绑定的，使用服务端 `request.user` 和 `conversation` 作为权限边界，没有把用户归属判断下放给前端。

### 4.5 前端页面

当前前端已经具备以下页面和入口：

- 聊天主页 `/`、`/chat`
- 登录页 `/login`
- 注册页 `/register`
- 设置页 `/settings`
- 管理员登录页 `/admin/login`
- 管理后台页 `/admin`

聊天页已实现：

- 左侧会话栏
- 新建会话
- 删除会话
- 发送消息
- 上传多个附件
- 流式渲染 assistant 回复
- 自动保持底部滚动
- 来源卡片展示

前端请求封装基本遵守契约，统一走 `frontend/src/services/`。

## 5. 当前核心实现方式

### 5.1 认证方式

当前不是 JWT，也不是 OAuth。

- 后端仍然使用 DRF token 作为认证凭证。
- 浏览器侧通过 Cookie 携带 token。
- `apiClient.js` 会为 `POST/PATCH/DELETE` 等请求自动注入 `X-CSRFToken`。
- 如果调用方改为手动带 `Authorization: Token ...` 请求头，则可绕过 Cookie 场景下的 CSRF 要求。

### 5.2 消息主链路

同步链路大致是：

`ChatPage -> chatApi.sendMessage/sendMessageStream -> Django API -> prepare_send_context -> Message/Attachment 落库 -> 检索 -> LangGraph -> assistant 消息落库 -> AgentRun 落库`

其中有几个关键现状：

- 附件允许先上传、后在发送消息时绑定到某条 user message。
- 新会话第一次发消息时，会把消息内容前 60 个字符写成会话标题。
- 即使 `OPENAI_API_KEY` 为空，系统也会返回 fallback 回复，并保留用户消息、AI 消息和运行记录。

### 5.3 RAG 实现方式

当前 RAG 不是独立向量数据库，而是 MVP 级实现：

- 文档文本解析后切分成 chunk
- embedding 向量直接存到 `KnowledgeChunk.embedding_json`
- 检索时在 Python 层计算余弦相似度

embedding 策略：

- 有 `OPENAI_API_KEY` 时优先调用远端 embedding
- 远端不可用时退回本地 `local-hash` 向量
- 检索阶段会按 `embedding_backend` 分组查询，避免不同维度/来源的向量混用

### 5.4 文档解析方式

- `.docx` 通过 `python-docx` 读取段落和表格文本
- `.pdf` 通过 `pypdf` 提取文本
- 扫描版 PDF 目前没有 OCR，提取不到文本时只能视为无可索引内容

## 6. 当前数据模型概览

后端当前核心数据对象包括：

- `Conversation`：用户会话
- `Message`：消息，`metadata_json` 承载 RAG 元数据
- `Attachment`：附件
- `AgentRun`：AI 调用记录
- `KnowledgeDocument`：附件级知识索引记录
- `KnowledgeChunk`：切片和 embedding
- `RetrievalLog`：检索命中日志
- `UserSettings`：用户主题、语言、字号等设置

当前本地数据库仍为：

- `backend/db.sqlite3`

这说明项目更偏开发/单机验证态，还没有演进到生产级数据库架构。

## 9. 当前限制与风险

下面这些不是“理论上可能有问题”，而是从当前实现能直接看出的现实边界：

### 9.1 数据与部署层面

- 数据库仍是 `SQLite`，更适合本地开发，不适合高并发生产使用。
- 向量检索不是独立向量库，而是 Python 遍历 + 余弦相似度，文档量增大后会先遇到性能瓶颈。
- 没有看到异步任务队列，文档索引仍是请求链路附近的同步逻辑，只是通过 `pending` 做了延后触发。

### 9.2 RAG 能力边界

- 检索范围只在当前会话，不支持全局知识库或跨会话检索。
- 当前只支持 `.docx` 和 `.pdf`。
- 扫描 PDF 没有 OCR，很多真实业务文档可能无法被有效索引。
- 来源展示已经有，但引用粒度仍以 chunk/snippet 为主，不是更严格的证据链系统。

### 9.3 认证与账号策略

- 当前是 token + cookie + CSRF 的自建方案，不是更完整的企业级认证体系。
- 密码强度校验函数已经存在，但注册和改密序列化器里没有真正阻断弱密码；前端也只是给出强度提示。这意味着“有密码强度逻辑，但当前并未强制执行”。

### 9.4 前端与工程化层面

- 前端仍是 CRA，不是更现代的 Vite/TypeScript 体系。
- 目前主要依赖命令级验证和后端单测，没有看到前端自动化测试。
- 路由采用 `HashRouter`，说明当前更偏向静态部署兼容，而不是完整服务端路由托管。

## 10. 当前可以如何判断项目成熟度

如果要一句话概括：

这是一个已经具备真实前后端链路、权限边界、基础安全、防护性上传校验、会话级 RAG 和流式回复的 AI 对话 MVP；它已经能支撑继续开发和内部验证，但还没有进入“生产级架构完成态”。

更具体地说：

- 不是原型：因为它有真实鉴权、真实数据库、真实上传、真实检索和测试。
- 也不是成品：因为它仍然使用 SQLite、本地向量方案、有限文档类型和较轻量的部署/工程化方案。

## 11. 建议作为下一阶段优先事项

如果后续继续推进，优先级最高的通常会是：

- 把数据库从 SQLite 迁移到 PostgreSQL
- 为文档索引补后台任务队列
- 为扫描 PDF 引入 OCR
- 评估是否需要真正的向量数据库
- 把密码强度校验从“提示”提升为“强制”
- 增加前端自动化测试和关键链路浏览器验证脚本
